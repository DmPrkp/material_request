# warehouse-server

Склады пользователей. NestJS + Drizzle, порт 4400, префикс `/warehouse/api/v1`, база `warehouse`.
Каркас взят у dictionary-server (гвард, фильтр ошибок pg, пагинация, миграции), но без
Scalar/OpenAPI и без локализации — клиента у сервиса пока нет.

## Доступ

Всё закрыто глобальным `AuthGuard` (`src/auth/`). Токен user-server проверяет nginx
(`nginx/njs/auth.js`) и передаёт пользователя заголовками `X-User-Id` / `X-User-Role` — сервис
секрета не знает. Без входа — `401`; битый токен и отсутствие секрета у nginx (`401` / `503`)
до сервиса не доходят. Поэтому на проде порт сервиса наружу не опубликован.

Склад заводит пользователь (`owner_id` = `sub`, из тела не принимается — лишнее поле даёт `400`).
Принадлежать склад может одной компании (`company_id`, многие к одной, без FK — компания в
company-server); без компании он личный. На склад назначаются пользователи (`warehouse_users`,
многие ко многим).

| действие                         | создатель | own/manage компании | назначенный | остальные |
| -------------------------------- | --------- | ------------------- | ----------- | --------- |
| видеть склад и назначенных       | да        | да                  | да          | `404`     |
| править, архивировать, удалять   | да        | да                  | `403`       | `404`     |
| назначать и снимать пользователей | `403`     | да                  | `403`       | `404`     |
| снять себя                       | —         | —                   | да          | `404`     |
| завести склад в компании / перенести в неё | — | да                | —           | `403`     |
| увести склад из компании         | `403`     | да                  | `403`       | `404`     |

Админ (`ADMIN` в токене) может всё. Назначить можно только участника компании склада (любая
роль) — иначе `400`; на личный склад — `409 personal_warehouse`. Сменить компанию можно только
без назначенных — `409 has_assigned_users`: они участники прежней компании. Уйдёт назначенный
из компании позже — назначение останется, пока его не снимут: company-server о складах не знает.
Правила — `src/modules/warehouses/access.ts`.

Роли и состав компании сервис спрашивает у company-server от имени пользователя, заголовками
`X-User-*`, по внутренней сети мимо nginx (`company.client.ts`, адрес — `COMPANY_URL`, по
умолчанию `http://company-server:4500/company/api/v1`). Не участник — `404` там, «ролей нет»
здесь. Сервис компаний лежит — `502`. Запрос уходит на каждое обращение к складу компании.

Список без фильтра — свои и назначенные, у админа тоже. `?companyId=` — склады компании:
её own/manage (и админ) видят все, остальные — свои и назначенные среди них.

## API

| Метод    | Путь                            | Что делает                                                                 |
| -------- | ------------------------------- | -------------------------------------------------------------------------- |
| `GET`    | `/warehouses`                   | `?page`, `?limit`, `?q` (название/адрес), `?state`, `?companyId`; у каждого `counts` — сколько наименований по видам |
| `GET`    | `/warehouses/:id`               | один склад                                                                 |
| `POST`   | `/warehouses`                   | `{ name, address?, description?, companyId? }`                             |
| `PATCH`  | `/warehouses/:id`               | те же поля, любые; `""` стирает необязательное, `companyId: null` — личный |
| `DELETE` | `/warehouses/:id`               | мягко (`is_active = false`), `?hard=true` — физически, с назначениями      |
| `POST`   | `/warehouses/:id/restore`       | вернуть архивный                                                           |
| `GET`    | `/warehouses/:id/users`         | назначенные: `userId`, `createdAt`                                         |
| `PUT`    | `/warehouses/:id/users/:userId` | назначить; повторно — не ошибка                                            |
| `DELETE` | `/warehouses/:id/users/:userId` | снять (свой id — отказаться самому), `204`                                 |
| `GET`    | `/warehouses/:id/items`         | что лежит на складе                                                        |
| `POST`   | `/warehouses/:id/items`         | `{ items: [{ kind, ref, quantity }] }` — пачка, одна транзакция            |
| `PATCH`  | `/warehouses/:id/items/:itemId` | `{ quantity }` — поставить вместо накопленного                             |
| `DELETE` | `/warehouses/:id/items/:itemId` | убрать позицию, `204`                                                      |
| `POST`   | `/warehouses/:id/items/remove`  | `{ items: [{ id, quantity }] }` — снять выбранное, `204`                   |
| `POST`   | `/warehouses/:id/items/move`    | `{ items: [{ id, quantity }], targetWarehouseId }` — на склад той же компании |
| `POST`   | `/warehouses/:id/items/issue`   | `{ items: [{ id, quantity }], userId }` — выдать на руки участнику компании |
| `GET`    | `/holdings/mine`                | всё, что у меня на руках, из всех компаний: позиции с `warehouseId`, `companyId` |

У `remove` и `move` количество можно взять частью: остаток остаётся лежать, всё — строка
уходит. Все или ничего: позиции нет на складе — `404`, просят больше, чем лежит, — `400`
(`planTakes` в `items.service.ts`), в обоих случаях не снимается ни одна.

Название уникально у создателя без учёта регистра среди действующих: дубль — `409`,
как и восстановление архивного при живом тёзке.

## Содержимое склада

Позиция (`warehouse_items`) названа так же, как в нормах расхода calc-server: `kind` —
`material | hand_tool | power_tool`, `ref` — код сборки (`7:227`, это `uniqKey` в заявке) у
материала и ручного инструмента, id позиции строкой у электроинструмента, сборок у него нет.
Названий здесь нет: их отдаёт словарь по тем же кодам. Перепишут сборку — код сменится, и на
складе останется прежняя позиция: это другая сборка, а не переименованная.

`quantity` — `numeric(14,4)` (складывают и правят руками, `0.1 + 0.2` не должно давать
`0.30000000000000004`), наружу уходит числом; ноль и отрицательное не принимаются. На пару
`(kind, ref)` — одна строка: повторное добавление складывается с лежащим, а не заводит вторую.

Ведёт содержимое любой, кому склад виден: создатель, назначенные и own/manage компании —
отдельного права «кладовщик» нет, назначение на склад и есть оно. `POST` берёт пачку позиций
и пишет её одной транзакцией: со страницы заявки уезжает весь её список, и половина принятых
позиций при обрыве связи хуже, чем ничего.

## На руках

«На руках» — склад с `holder_user_id`: не место, а человек, которому компания выдала
позиции. Он всегда компании (выданное — её имущество) и один на человека в компании
(`warehouses_holder_uq`), так что у работающего в трёх компаниях — трое «рук». Заводит их
первая выдача, заранее никто; `owner_id` — выдавший первым, прав это не даёт.

- **Выдать** (`…/items/issue`) — со склада компании (не с личного и не с рук) участнику
  этой компании, в том числе себе. Выдаёт тот, кто ведёт содержимое склада, назначенный
  кладовщик тоже. Списание и зачисление — одна транзакция, как у `move`.
- **Вернуть** — обычный `move` с рук на склад той же компании. На руки `move` не кладёт:
  только выдачей, она проверяет, что получатель в компании.
- **Видят** руки держатель и own/manage компании (и админ). Держатель своё только видит:
  вернуть и списать может own/manage — иначе это вынос мимо учёта.
- В `GET /warehouses` рук нет — это люди, а не места. Переименовать, архивировать и
  назначить на них нельзя (`409 holding`), удалить физически — own/manage.

## База

Схема — `src/db/schema.ts`, миграция — `drizzle/0000_init.sql` (`npm run db:generate`; пока
проект не развёрнут, миграция одна — перед генерацией удалить `drizzle/`). `npm run db:migrate`
сам заводит базу, если её нет: `db/init` срабатывает только на пустом томе. Нет прав на `CREATE DATABASE` — базу надо завести руками.

Env — общий `.env` в корне (`.env.example`), `POSTGRES_DB=warehouse` задан в compose.
