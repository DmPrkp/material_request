# dictionary-server

Справочник материалов, инструментов и параметров.

## Что здесь есть

| Таблица                                    | Что хранит                                  | Было в calc-server                         |
| ------------------------------------------ | ------------------------------------------- | ------------------------------------------ |
| `units`                                    | единицы измерения                           | свободная строка `measure` в трёх таблицах |
| `param_kinds`                              | виды параметров: длина, диаметр, напряжение | `params_titles`                            |
| `param_values`                             | значения параметров (`NUMERIC` + единица + вид) | `params` (значение строкой)            |
| `work_types`                               | виды работ: фасад, кровля, внутр. отделка   | не было (жило в меню клиента)              |
| `systems`                                  | технологии работ, `work_type_id` → вид; `title` — код, людям — `name_*` | `systems`              |
| `work_stages`                              | этапы/слои работ внутри технологии; `title` — код, людям — `name_*`     | `components`           |
| `material_types`                           | типы материалов: пиломатериалы, крепёж, леса | не было                                    |
| `hand_tools` / `power_tools` / `materials` | позиции каталога                            | одноимённые                                |
| `hand_tool_variants` / `material_variants` | типоразмеры позиций                         | `assembled_*`                              |
| `*_variant_params`                         | параметры типоразмера                       | `hand_tool_params` / `material_params`     |

Чего здесь **нет**: норм расхода. Они остались в `calc-server`
(`hand_tool_norms`, `power_tool_norms`, `material_norms`) и ссылаются на
`work_stage_id` и `*_variant_id` из этой базы обычными `INTEGER` — межбазовых
внешних ключей в Postgres не бывает.

## Запуск

```
docker compose -f compose.dev.yaml -p matli-dev up -d db dictionary-server
```

Документация: http://localhost:4300/dict/api/v1/docs
Спека: http://localhost:4300/dict/api/v1/openapi.json

## Язык ответа

В базе имя и описание хранятся на двух языках (`name_ru` / `name_en`), а в ответе
поле одно — `name`, `description` — на языке из `Accept-Language`:

```
curl -H 'Accept-Language: en' http://localhost:4300/dict/api/v1/materials
```

Без заголовка или с неизвестным языком — русский. На запрошенном языке пусто — отдаём
ближайшее заполненное: сначала русское, потом остальные. Технологии и этапы с клиента
пишутся только на языке, на котором работал человек (хоть одно название обязательно —
`CHECK *_name_present`), и заведённое под `/en` под `/ru` покажется по-английски. Сворачивается
любая пара `xRu`/`xEn` в любом месте ответа (`src/common/localize.ts`), так что новая
двуязычная колонка подхватится сама. Создание и правка по-прежнему принимают оба поля.

Форме правки нужны оба языка сразу — для неё `?translations=all` отдаёт поля как
в базе (`nameRu`, `nameEn`…), без сворачивания. Больше этим никто не пользуется.

## Кто может писать

Чтение открыто всем. Запись в `systems` и `work-stages` — только с токеном
user-server (`Authorization: Bearer <accessToken>`), и создание запоминает автора
в `created_by` (id пользователя, `NULL` у строк из сидов).

Словарь проверяет подпись токена сам, общим `JWT_SECRET` из `secrets/jwt/.jwt.env`,
и в базу пользователей не ходит: удалённый пользователь может писать, пока не истечёт
его токен. Без `JWT_SECRET` защищённая запись отвечает `503`.

Включается опцией `authored: true` в `createDictionaryController()` — у таблицы
должна быть колонка `createdBy` (`authorship` в `schema.ts`).

## Вид параметра — на значении, а не на связке

`param_values.kind_id` говорит, что такое это число: длина, диаметр, напряжение.
Раньше вид лежал на `*_variant_params`, то есть на связке типоразмера со
значением — и одно и то же «8 мм» помечалось `diameter` у дюбель-гвоздя и
`length` у дюбеля фасадного. БД такому не мешала, ловилось только глазами.

Теперь у значения ровно один вид, а уникальность — по тройке
`(kind_id, value, unit_id)` с `NULLS NOT DISTINCT`:

- «100 мм как длина» и «100 мм как ширина» — две разные строки, это законно;
- два одинаковых «100 мм длины» — отказ;
- два «100 мм без вида» — тоже отказ, обычный `UNIQUE` их бы пропустил.

`kind_id` необязателен: у 91 значения из 118 вид в исходных данных не задан —
это метры для рулеток и неиспользуемые значения. Проставляется через
`PATCH /param-values/:id`.

## Типы материалов

`materials.type_id` — необязательная ссылка на `material_types`: тип у материала
может отсутствовать. Сейчас проставлен у всех 44 позиций.

```
GET /materials?typeId=7      # только пиломатериалы
GET /materials?untyped=true  # те, у кого тип ещё не проставлен
```

## Удаление позиций

`DELETE /:id` по умолчанию **архивирует** (`is_active = false`): позиция
пропадает из выдачи, но расчёты, где она уже участвует, не ломаются.

`DELETE /:id?hard=true` удаляет физически и возвращает `409` со списком того,
что мешает. Проверяются только ссылки **внутри этой базы** — нормы расхода
в `calc-server` отсюда не видны, поэтому для позиций, участвующих в расчёте,
пользуйтесь мягким удалением.

## Схема БД

Единственный источник правды — `src/db/schema.ts`. В dev схема
синхронизируется командой `drizzle-kit push` при старте контейнера.

> `push --force` **удаляет из базы всё, чего нет в схеме**, включая служебные
> таблицы. Поэтому `seed_history` объявлена в `schema.ts`, хотя приложение
> с ней не работает.

Когда справочник устаканится, переходите на обычные миграции:

```
npm run db:generate     # создаст SQL в drizzle/
npx drizzle-kit migrate
```

## Сиды

Данные лежат в `src/db/seed-data/*.ts` типизированными массивами, заливка —
`src/db/seed.ts`. Шаги именованные, каждый в своей транзакции и с отметкой
в `seed_history` — контейнер гоняет `db:seed` при каждом старте, а том переживает
рестарт, и без отметок вторая заливка упала бы на duplicate key.

Правка уже применённого шага до базы не доедет. Справочник пока не в проде,
поэтому данные чинятся правкой сидов и пересозданием базы:

```
docker compose -f compose.dev.yaml -p matli-dev down -v
```

Главное: **`code` варианта в данных не хранится**. Он собирается функцией
`buildVariantCode()` из `src/modules/catalog/variant-code.ts` — той же самой,
которой пользуется API при создании варианта. Одно правило, одно место.

Пока код вбивали руками в SQL, он успел разойтись с параметрами в трёх
вариантах из двухсот — и увидеть это можно было только сплошной сверкой.
Теперь такое расхождение невыразимо: код неоткуда взять, кроме как вычислить.

`id` проставляются явно и намеренно — нормы расхода в `calc-server` ссылаются
на конкретные `*_variant_id`, и раздача новых id через identity их бы осиротила.
Поэтому после заливки sequence сдвигаются на `max(id)`.

Гарантия держится на договорённости, а не на БД: прямой `INSERT` из psql
по-прежнему может записать любой код. Если понадобится защита на уровне базы —
это триггер на `*_variant_params` плюс отложенный `UNIQUE` на `code`.
